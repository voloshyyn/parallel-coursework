# Architecture

## Мета
Контейнеризована пошукова система, що демонструє паралелізм на всіх етапах:
паралельна побудова інвертованого індексу, потокобезпечна структура даних, паралельна обробка запитів клієнтів.

Пайплайн пошуку: **query expansion (Ollama) → keyword search (інвертований індекс) → результат (REST / WebSocket)**.

## Компоненти

| Компонент | Відповідальність |
|---|---|
| HTTP/WebSocket-сервер | Прийом запитів, маршрутизація, паралельна обробка клієнтів |
| Indexer | Читання файлів датасету, токенізація, подача задач у thread pool |
| IndexService | Перелік файлів, паралельна побудова, атомарна публікація готового індексу |
| Thread pool (власний) | Фіксована кількість робочих потоків, черга задач, graceful shutdown |
| Inverted index (власний) | Потокобезпечне відображення `term → postings`, паралельний запис і читання |
| Search engine | Розбір запиту, пошук за термінами, ранжування (score), snippet |
| Ollama client | HTTP-виклик `/api/generate`, розбір розширених термінів, таймаут і fallback |
| Pipeline | Послідовність етапів + подія на кожен етап для WebSocket |
| CLI-клієнт | `./search "запит"` |
| Web UI | Форма пошуку, візуалізація етапів через WebSocket |

## Шари
```
Clients (CLI, Web UI)
        │  REST / WebSocket
API layer (handlers, DTO, валідація)
        │
Service layer (IndexService, SearchPipeline)
        │
Core (ThreadPool, InvertedIndex, Tokenizer)      Integrations (OllamaClient)
```

## Потокобезпека
Прийняті рішення (відповіді на питання 9, 12, 13, 18 захисту):
- **Індекс:** шардований. Термін хешується в один із N шардів (N ≈ 16–64), кожен шард має власний `std::shared_mutex`. Пошук бере shared lock, запис — exclusive lock лише на свій шард.
- **Побудова:** потоки пишуть напряму у спільний шардований індекс, без локальних індексів і merge. Так виконується вимога «структура даних з паралельним доступом».
- **Пошук під час побудови:** нові пошукові запити під час первісної побудови
  або перебудови отримують 409 `index is building`. Запити, що вже почалися до
  початку побудови, можуть завершитися зі своїм снимком.
- **Публікація індексу:** `POST /api/index` будує новий індекс окремо від
  опублікованого снимка і публікує його атомарно разом зі статистикою побудови
  (`PublishedIndex`: `shared_ptr<const InvertedIndex>` + `BuildStats`). Тому
  напівзбудований індекс ніколи не публікується, невдала перебудова залишає
  попередні індекс і статистику робочими, а `/api/stats` бере `documents`,
  `index_build_time_ms` і `threads_used` з однієї успішної побудови. Одночасно
  виконується лише одна побудова, друга дістає 409.
- **Стан побудови:** перевірка «чи вже будується» і перехід
  `kBuilding → kReady/kEmpty` виконуються під одним мьютексом, тому наступна
  побудова не може початися до завершення переходу попередньої. Перелік,
  читання й індексування файлів ідуть поза цим мьютексом.
- **Блокування:** кожна операція бере не більше одного lock, тому циклічного очікування (deadlock) бути не може.
- **Thread pool:** блокуюча черга задач (`std::mutex` + `std::condition_variable`). Завершення через `shutdown()`, яке чекає виконання вже поставлених задач. Виняток у задачі перехоплюється і логується, пул не падає.

## Токенізація та індекс

Реалізація: `src/core/tokenizer.*`, `src/core/inverted_index.*`.

- **Токен** — максимальний неперервний фрагмент з літер і цифр. Літера — це
  ASCII-літера/цифра або будь-який код-пойнт UTF-8, що не є пунктуацією чи
  символом: розділювачами вважаються пробіли, ASCII-пунктуація, блок
  U+2000–U+206F (тире, «розумні» лапки), U+00A0–U+00BF, `×`, `÷`, CJK-пунктуація
  та невалідні UTF-8-послідовності. Тому `don't` → `don`, `t`; `word—word` →
  `word`, `word`; `C++20` → `c`, `20`.
- **Регістр:** згортаються ASCII та кирилиця (А–Я, Є, І, Ї, Ґ), щоб `Дніпро`
  збігалося з `дніпро`. Інші мови не згортаються: ICU не підключаємо.
- **Без стемінгу і стоп-слів:** пошук іде за точним токеном, а фільтр стоп-слів
  зламав би пошук за короткими запитами.
- **Документ:** зовнішній `doc_id` (рядок) → внутрішній `DocId` (`uint32`).
  Повторний `doc_id` — помилка; перебудова створює новий індекс і публікує його
  атомарно, тому `Clear()` (небезпечний паралельно з `AddDocument()`) у
  серверному шляху не використовується.
- **Posting:** пара `(DocId, term_freq)`, 8 байт; `term_freq` — скільки разів
  термін зустрічається в документі. Довжина документа в токенах зберігається
  окремо — знадобиться для нормування `score`.
- **Шарди:** 32 за замовчуванням, конструктор приймає будь-яке `N ≥ 1`. Термін
  потрапляє в шард за `hash(term) % N`. `AddDocument()` групує терміни за шардами
  і бере exclusive lock на кожен шард один раз за документ; `Lookup()` бере
  shared lock. Жодна операція не тримає два локери одночасно.
- **Пам'ять:** постінги лежать у `std::vector` всередині шарда (по одному
  вектору на термін), тому накладні витрати — це `unordered_map` шарда плюс
  запас `vector`.

## Розширення запиту (Ollama)

Реалізація: `src/integrations/ollama_client.*`, `src/services/search_pipeline.*`.

- **Виклик:** `POST /api/generate` з моделлю з `OLLAMA_MODEL`, `stream: false`,
  `options.temperature: 0` і промптом, що просить список синонімів та ключових
  слів через кому. Відповідь читається з поля `response`.
- **Розбір:** відповідь проходить той самий токенізатор, що й індекс: терміни
  згортаються в нижній регістр, дублікати й терміни, що вже є в запиті,
  відкидаються, лишається не більше 8 термінів. Тому «синонім» означає для
  пошуку те саме, що й звичайний токен документа.
- **Таймаути:** health-перевірка — 500 мс, генерація — 5 с (модель 1,5B на CPU
  відповідає за секунди). Мережева помилка, таймаут, відповідь не-200 або
  некоректний JSON дають порожній список.
- **Пайплайн:** `SearchPipeline` спочатку отримує розширення (best effort), потім
  шукає за об'єднанням оригінальних і розширених термінів. Порожній список або
  виняток у розширювачі не змінюють пошук: він іде за оригінальним запитом.
  `time_ms` у відповіді REST — час лише keyword-пошуку.
- **Контракт:** REST не показує розширені терміни (такого поля немає в
  `api.md`); їх віддаватиме WebSocket-подія `query_expansion` (етап 6).

## Ранжування та снипети

Реалізація: `src/core/search_engine.*`.

- **Score:** TF-IDF. Внесок терміна — `tf / довжина_документа * idf`, де
  `idf = ln(1 + N / df)`, `N` — кількість документів, `df` — скільки документів
  містять термін. Повторення терміна в запиті не впливає на score (терміни
  дедуплікуються).
- **Нормування:** score ділиться на найкращий, тому відповідь містить значення
  в (0, 1], а перший результат завжди має `score = 1.0`.
- **Порядок:** спочатку за score (спадання), при рівності — за `doc_id`
  (зростання); видача детермінована.
- **Кількість:** не більше 10 результатів (у контракті немає поля `limit`).
- **Снипет:** вікно 80 символів до і 120 після першого токена документа, що
  дорівнює одному з токенів запиту. Документ розбирається тим самим
  токенізатором, що й індекс, тому `cat` не збігається з `education`, а регістр
  згортається за тими самими правилами (ASCII і кирилиця). Пробіли згортаються,
  межа вікна не розрізає UTF-8-послідовність. Текст документів на диску;
  снипет читається з файлу за `doc_id` (до 10 читань на запит).

## Потік даних: пошук
1. Клієнт надсилає запит (REST або WebSocket).
2. Pipeline викликає Ollama → `expanded_terms` (подія `query_expansion`).
3. Search engine шукає за оригінальними й розширеними термінами (подія `keyword_search`).
4. Подія `done`; для REST повертається один підсумковий JSON.
